# Dependency Injection (Fowler)

Martin Fowler, 2004. Core problem: как собрать плагины в приложение так, чтобы код не зависел от конкретных реализаций.

## Ключевые тезисы

1. **IoC слишком общий термин** -- фреймворки инвертируют контроль по определению. Конкретная инверсия здесь: как компонент находит реализацию плагина. Fowler предлагает имя "Dependency Injection"

2. **Три формы DI**: constructor injection (предпочтителен -- валидный объект с рождения, immutable поля), setter injection (много зависимостей, опциональные), interface injection (наиболее инвазивный, требует специальные интерфейсы)

3. **Service Locator** -- альтернатива DI. Явный запрос к локатору. Зависимость от самого локатора, но поведение прямолинейнее. Для классов внутри одного приложения ~= эквивалентен DI. Для компонентов, используемых в разных приложениях -- DI лучше (нет привязки к конкретному локатору)

4. **Constructor vs Setter**: начинать с constructor, переключаться на setter при проблемах (много параметров, опциональные зависимости, несколько путей конструирования)

5. **Фундаментальный принцип**: separating configuration from use -- важнее выбора между DI и Locator. Аналог разделения интерфейса и реализации. Конфигурация решает какой класс; использование опирается на полиморфизм

6. **Plugin pattern** (P of EAA): класс-реализация не привязан в compile time, подставляется позже, вне контроля автора компонента

7. **Код vs конфиг-файлы**: всегда предоставлять программный интерфейс, конфиг -- опционально. Over-eagerness для конфиг-файлов -- проблема
