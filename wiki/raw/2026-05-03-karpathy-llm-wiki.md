# LLM Wiki — Karpathy

Источник: https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f (апрель 2026)

## Суть паттерна

RAG-подход: LLM извлекает релевантные чанки из сырых документов при каждом запросе. Знание не накапливается — каждый вопрос требует повторного синтеза. NotebookLM, ChatGPT file uploads, большинство RAG-систем работают так.

LLM Wiki — иной подход: LLM **инкрементально строит и поддерживает постоянную wiki** — структурированную, взаимосвязанную коллекцию markdown-файлов между пользователем и сырыми источниками. При добавлении нового источника LLM не просто индексирует — читает, извлекает ключевое, интегрирует в существующую wiki: обновляет страницы сущностей, пересматривает обзоры тем, отмечает противоречия, усиливает или оспаривает синтез.

**Wiki — постоянный, нарастающий артефакт.** Cross-references уже построены. Противечия уже помечены. Синтез уже отражает всё прочитанное. Wiki обогащается с каждым источником и каждым вопросом.

Человек не пишет wiki — LLM пишет и поддерживает всё. Человек курирует источники, направляет анализ, задаёт вопросы. LLM делает всю рутину: суммаризация, cross-referencing, ведение, bookkeeping.

## Три слоя

1. **Raw sources** — курируемая коллекция исходных документов (статьи, papers, изображения, данные). Immutable — LLM читает, не модифицирует. Source of truth.
2. **The wiki** — директория LLM-генерируемых markdown-файлов. Суммаризации, страницы сущностей, концепты, сравнения, обзор, синтез. LLM владеет этим слоем полностью: создаёт, обновляет, поддерживает cross-references, обеспечивает консистентность. Человек читает; LLM пишет.
3. **The schema** — документ (CLAUDE.md / AGENTS.md / etc.), описывающий структуру wiki, конвенции, workflows для ingest, query, lint. Ключевой конфигурационный файл. Ко-эволюционирует с пользователем и LLM по мере понимания домена.

## Операции

### Ingest
Пользователь кладёт источник в raw и просит LLM обработать. Поток: LLM читает источник → обсуждает ключевые выводы → пишет summary-страницу → обновляет index → обновляет релевантные entity/concept страницы → добавляет запись в log. Один источник может затронуть 10-15 wiki-страниц. Предпочтительно обрабатывать по одному источнику с вовлечением — читать summaries, проверять обновления, направлять LLM.

### Query
Пользователь задаёт вопросы против wiki. LLM ищет релевантные страницы, читает, синтезирует ответ с цитатами. Ответы могут быть разных форматов: markdown, таблица, слайды (Marp), chart (matplotlib). **Ключевой инсайт: хорошие ответы можно filed обратно в wiki как новые страницы.** Сравнение, анализ, обнаруженная связь — не должны исчезать в истории чата. Так исследования нарастают в knowledge base как и ingested sources.

### Lint
Периодическая проверка здоровья wiki. Искать: противоречия между страницами, устаревшие утверждения, orphan-страницы без входящих ссылок, упомянутые но не раскрытые концепции, пропущенные cross-references, пробелы в данных. LLM хорош в предложении новых вопросов и источников для исследования.

## Навигация: index.md и log.md

**index.md** — content-oriented. Каталог всего в wiki: каждая страница с ссылкой, однострочным summary, опциональными метаданными (дата, число источников). Организован по категориям. LLM обновляет при каждом ingest. При ответе на query LLM сначала читает index, затем drill-down в страницы. Работает до ~100 источников, ~сотен страниц. Избегает необходимость в embedding-based RAG.

**log.md** — chronological. Append-only запись что произошло и когда — ingests, queries, lint passes. Совет: консистентный префикс (`## [2026-04-02] ingest | Article Title`) делает log parseable unix-инструментами — `grep "^## \[" log.md | tail -5`.

## Применения

- Персональное: цели, здоровье, психология, self-improvement — journal entries, статьи, podcast notes
- Исследования: глубокое погружение в тему за недели/месяцы — papers, articles, reports, нарастающая wiki с эволюционирующим тезисом
- Чтение книги: каждая глава по мере прочтения, страницы для персонажей, тем, сюжетных линий. К концу — богатая companion wiki. Как fan wikis (Tolkien Gateway), но лично
- Бизнес/команда: внутренняя wiki, fed by Slack threads, meeting transcripts, project docs. Humans in the loop reviewing updates
- Конкурентный анализ, due diligence, планирование поездок, курсовые заметки, hobby deep-dives

## Почему это работает

Трудная часть ведения knowledge base — не чтение или мышление, а bookkeeping. Обновление cross-references, актуальность summaries, отметка противоречий, консистентность по десяткам страниц. Люди бросают wiki потому что бремя поддержки растёт быстрее ценности. LLM не скучает, не забывает обновить cross-reference, может затронуть 15 файлов за один проход. Wiki поддерживается потому что стоимость поддержки ≈ 0.

Связано с Memex Ванневара Буша (1945) — персональное, курируемое хранилище знаний с ассоциативными следами между документами. Чего Буш не смог решить — кто делает поддержку. LLM справляется.

## Примечание

Документ намеренно абстрактен. Описывает идею, не реализацию. Точная структура директорий, конвенции schema, форматы страниц, tooling — зависит от домена, предпочтений, LLM. Всё опционально и модульно. Правильный способ — поделиться с LLM-агентом и совместно инстанцировать версию под свои нужды.
