# ФП в JS — два источника

## Источник 1: Хабр (Альфа-Банк, декабрь 2025)

URL: https://habr.com/ru/companies/alfa/articles/975256/

Как ФП изменило фронтенд и почему отрасль возвращается к платформе.

### Исторический контекст

В начале 2010-х jQuery-код был императивным, хрупким, не масштабировался. ФП предложило модель: UI = f(state). React заложил фундамент, Elm повлиял на взгляды, Redux упаковал: однонаправленный поток данных, иммутабельность, явные действия. React Hooks закрепили тенденцию.

### Почему ФП-идеалы плохо ложатся на веб

Веб-платформа построена на side effects:
- CSS — стили распространяются за пределы компонента
- DOM — огромное изменяемое дерево, браузеры оптимизируют десятилетиями
- Пользовательские действия — непредсказуемы, асинхронны, конкурентны
- HTML — декларативный, описывает структуру без JS

Веб не чистый и не стремится быть чистым. Обратная совместимость и гибкость — не баг, а фича.

### Абстракции поверх платформы

Желание «очистить» фронтенд привело к избыточным абстракциям:
- CSS → CSS-in-JS (рантайм-генерация, тяжёлые бандлы, задержки рендера)
- События → Synthetic Events (дополнительный слой)
- Модалки → игнорирование нативных `<dialog>` (порталы, фокус, escape вручную)
- Навигация → переизобретение маршрутизации вместо History API
- Формы → кастомные фреймворки вместо нативной валидации
- SSR → гидратация (повторный расчёт UI когда HTML уже на странице)

Проблема: вместо применения ФП где уместно, индустрия стала применять его везде. React стал default. Цикл: вакансии требуют React → разработчики учат React → вакансии требуют React.

### Разворот 2020-х

- Astro — островная архитектура, минимум клиентского JS
- HTMX — гипертекст всё ещё мощный
- SvelteKit — компиляция, без тяжёлых рантаймов
- Qwik — ленивая загрузка, без полной гидратации

Эти инструменты не отказываются от ФП-идей, они отказываются переделывать веб под ФП. Принимают платформу: DOM, CSS, нативные события, HTML.

### Вывод

ФП остаётся полезным **внутренним принципом**, но перестаёт быть архитектурной религией. Чрезмерная чистота усложняет не меньше, чем бардак. Вопрос не «Нужно ли ФП фронтенду?», а «Каким оно должно быть именно для веба?» — приземлённое «веб-ФП» поверх того, что браузер делает хорошо.

## Источник 2: GitHub — damiancipolat/Functional_programming_in_JS

URL: https://github.com/damiancipolat/Functional_programming_in_JS

Каталог ФП-концептов в JS с примерами. Без анализа границ применимости.

### Концепты (с примерами)

- **Pure functions**: одинаковый вход → одинаковый выход, нет side effects
- **Side effects**: любое изменение состояния за пределами функции (DOM, сеть, логирование, глобальные переменные)
- **Referential transparency**: выражение можно заменить на его значение без изменения поведения программы
- **High-order functions**: функции принимающие/возвращающие функции (map, filter, reduce)
- **First-class functions**: функции как значения — сохранение в переменные, передача как аргументы, возврат из функций
- **Compose**: f(g(x)) — композиция функций, конвейер обработки данных
- **Curry**: функция с N аргументами → N функций с 1 аргументом. `f(x,y,z) → f(x)(y)(z)`
- **Lambda**: функция как данные (аргумент/возврат/присваивание), не то же что анонимная функция
- **Closure**: функция + лексическое окружение (замыкание переменных внешнего scope)
- **Stateless**: операции не зависят от состояния, все данные через входы, все результаты через выходы
- **Recursion**: самовызов вместо циклов. В JS — риск stackoverflow. Решение: trampoline
- **Lazy evaluation**: отложенное вычисление через thunks `() => expr`
- **Functor**: объект, который можно отобразить (map). Array — фундаментальный functor
- **Monoid**: множество с ассоциативной операцией и нейтральным элементом (String+concat, Number+add, Functions+compose)
