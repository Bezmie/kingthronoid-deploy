# Функциональное программирование в JS

Парадигма, основанная на чистых функциях, иммутабельности и явных side effects. В JS-проектах — не догма, а набор инструментов.

Источник: sources frontmatter

## Ключевые принципы

| Принцип | Суть | Когда полезно |
|---|---|---|
| **Pure functions** | Одинаковый вход → одинаковый выход, нет side effects | Вычисления, формулы, бизнес-логика |
| **Immutability** | Данные не мутируются, создаются новые копии | State management, undo/redo |
| **Referential transparency** | Выражение заменимо на его значение | Оптимизация, memoization, тестирование |
| **High-order functions** | Функции как аргументы/возврат (map, filter, reduce) | Трансформации коллекций |
| **Compose** | f(g(x)) — конвейер функций | Data pipelines, middleware |
| **Curry** | f(x,y,z) → f(x)(y)(z) — частичное применение | Конфигурация, reuse |
| **Stateless** | Операции не зависят от внешнего состояния | Тестируемость, предсказуемость |

## Границы применимости во фронтенде

Веб-платформа построена на side effects (DOM, CSS, события). ФП-идеалы плохо ложатся на платформу:

- CSS — каскад распространяется за пределы компонента
- DOM — изменяемое дерево, десятилетия оптимизаций браузеров
- События — непредсказуемы, асинхронны, конкурентны
- HTML — декларативный, работает без JS

Попытки «очистить» веб привели к избыточным абстракциям: CSS-in-JS, Synthetic Events, кастомные роутеры, гидратация. Индустрия 2020-х разворачивается к платформе (Astro, HTMX, SvelteKit, Qwik).

**Вывод**: ФП — полезный внутренний принцип, но не архитектурная религия. Чрезмерная чистота усложняет не меньше, чем бардак. Правильный подход — **«приземлённое ФП»**: чистые функции где уместно, но не против природы платформы.

## Применение в проекте

Pragmatic FP: чистые функции в compute-слой, mutable state в systems (осознанный tradeoff для game loop), EventBus = контролируемые side effects. Иммутабельность ограничена (Decimal immutable, но state mutable — GC-нагрузка 60fps невыгодна).
